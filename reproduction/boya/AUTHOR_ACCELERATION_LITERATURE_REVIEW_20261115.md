# 原文与现成加速方案核查：当前耗时不是算法速度下限

用户质疑现有速度，并要求查原文／网络方案与创新空间。本轮只做文献、源码和既有阶段回执核对，0新Kit／物理／标签／训练，未安装依赖或改变冻结采集协议。

结论：现成路线明确存在。当前应先修完整采集流水线与已知实现开销，再谈是否需要新算法；前次27–33天只是原样延续试采配置的条件情景，不是AnyDexGrasp的必需成本。

## 原文和原代码能确认什么

原文报告0.5s生成200个姿态，CPU碰撞检测20s，并明确未做该步加速。它们是局部耗时，不能作为完整标签采集速度。[AnyDexGrasp原文，第3.1节](https://arxiv.org/html/2502.16420v1)

作者采集代码在 `robot_grasp` 的循环外建立网络、机器人和手云，随后复用。当前20次Kit冷启动属于本机仿真实现的生命周期成本。[原采集代码](https://github.com/graspnet/AnyDexGrasp/blob/main/collect_dh3_grasp_data.py#L368-L394)

## 不能忽略已经做过的工作

同组三体四型常驻已经实测，旧同组完整流程历史比较约1.52倍；八路CPU执行与两路审核也已经集成。尾批每个手型独立冷session，20Kit中10次capture、10次execution，仍不是整个采集阶段的常驻资产池。待补的是跨阶段／跨几何组合的生命周期复用与流水安排，不能把旧常驻循环再宣布一次为新成果。

GPU单／双环境已经接通，但旧20tick实测约91%的前缀耗时在fetch_results，接触读取只占很小部分。因此不能声称只改主机读回就能解决GPU慢，也不能按文档env数外推吞吐。需要先解释实际物理等待和GPU兼容性，再选择规模；本轮未追加任何GPU试验。

## 用本批实测决定优先级

92个阶段回执按实际时间区间合并，执行／审核重叠只计一次：

| 环节 | 尾批占用时钟 |
|---|---:|
| 建场＋观测初始化＋初始化审核 | 16.506分钟 |
| 原规划准备 | 8.759分钟 |
| 执行＋抓取审核，扣重叠 | 20.667分钟 |
| CGR推理 | 0.432分钟 |
| 其余派发／交接／导出等 | 1.554分钟 |

这些仍是阶段成本，不能继续把执行段未经实测拆成GPU kernel、物理、序列化或几何各自占比。40个实际准备槽中30个无候选／几何拒绝，只有10个进入执行；另20槽为预先确定的placement_null。产率问题也要单独定位，不能只靠加worker解决。

建议按以下顺序做独立实现，保持原候选／标签定义：

1. 先把已经验证过的常驻基础接到完整采集生命周期，减少20次冷启动与重复资产导入；用已有跨几何重建分支作为接点，不另造环境框架。新分支需要实际完整对照，当前不冒称已验收。
2. 用官方资产复制／隔离和流水安排，把观测、准备、执行、审核重叠；完整点数据可优化批量表示／读取，保留全部字段和原独立数值判定。
3. 在独立环境固定cuRobo版本，先验证本机器人运动学／碰撞，再比较规划成本。它改变规划器，需单独版本，不能回写原命令或称轨迹等价。
4. 对此前GPU慢做资产GPU兼容性和实际物理等待核查；确认原因后再决定较大批量实验。不能把CPU回退作为已经查明的故障，也不能把别人的毫秒结果当本机结果。

接受标准是同一冻结预算下的完整墙钟、每型合格标签产率、全部物理门／标签兼容性及资源成本，不能只报某个kernel或规划查询的倍数。正式fit/internal尝试预算另冻，不按本轮观察临时换候选、放门或挑容易物体。

## 创新判断

常驻、克隆、多环境GPU验证和GPU规划都有公开先例。现有资料足以否定“没有现成路线只能从零发明”的判断，但不能据此保证本机一定达到某个倍数。

如果在这些基线上仍有显著瓶颈，可研究“在保留原候选分布和标签定义的条件下，降低复杂灵巧手采集与验证的成本”。是否构成创新，需要新的方法、清楚的现有基线和完整实验；一次搜索没有找到直接可用代码不等于新颖性证明。
